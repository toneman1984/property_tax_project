# Property Tax Project — Pipeline Plan

## Research Question

Are homeowners in Travis County fraudulently claiming the homestead exemption on properties
they aren't using as a primary residence? Two earlier approaches to this question — a
neighborhood-level STR/Airbnb density correlation, then a parcel-level ML risk model — were
built out, produced real results, and were archived; see `docs/fraud_model_pivot.md` for the
full decision history. The project is currently in an EDA-first phase: a deep, systematic
re-exploration of the raw TCAD source data (`docs/tcad_eda/`) before committing to any
modeling approach again.

---

## Prerequisites

Before running the pipeline, every file listed in `scripts/load_protax_to_sqlite.py`'s
`JSON_FILES` must be present in `data/sources/` — one per appraisal-year vintage:

| File | Vintage | Description | How to obtain |
|---|---|---|---|
| `Travis_protaxExport_20250720.json` | 2025 | TCAD property tax export (~27GB) | Run `python scripts/fetch_tcad.py` |
| `Travis_protaxExport_20260731.json` | 2026 | TCAD property tax export (~28GB) | Run `python scripts/fetch_tcad.py` |

`fetch_tcad.py` downloads and extracts every export in its `EXPORTS`/`SELECTED_EXPORTS` config
from traviscad.org. It skips the download for any ZIP already present in `data/sources/`. Note
(found 2026-08-17): traviscad.org started rejecting the default `requests` User-Agent with a
403 at some point — `fetch_tcad.py` now sends a browser-like User-Agent header to work around
this; if downloads start failing again, that's the first thing to check.

(The STR permit and Airbnb listings files used by the archived POC are no longer prerequisites
for the active pipeline — see `archive/docs/poc_pipeline_plan.md` if reviving that approach.)

## Pipeline

Run the pipeline with:

```
python main.py
```

`main.py` runs only Stage 1 — ingestion is the one settled, validated step, and as of
2026-08-17 it builds everything the project currently extracts from the raw export(s) in one
streaming pass per file, 20 tables, all keyed by `(pID, pYear)` rather than `pID` alone (see
"Multi-vintage support" below). Its preflight/output-test logic lives in `scripts/checks.py` (a
single registry keyed by checkpoint name, currently just `"stage1"`), not a per-stage file —
reached via `run_checkpoint("stage1", build_fn=...)`.

### Stage 0/1 — Preflight + Load TCAD JSON to SQLite
**Scripts:** `scripts/checks.py` (checkpoint `"stage1"`) + `scripts/load_protax_to_sqlite.py`
**Status:** Complete

`run_checkpoint("stage1", ...)` first checks whether a valid SQLite database already exists
(file size ≥ 0.5 GB, all 20 expected tables present with plausible row counts) so that Stage 1
(~20-25 minutes for 2 vintages, streaming each ~28GB export once) can be skipped if the
database is already built. If preflight fails, `load_protax_to_sqlite.py` streams each file in
`JSON_FILES` with `ijson` (never loads the full file into memory) and inserts records in
batches of 10,000, building:

- `properties` — top-level parcel fields (propType, geometry, inactive, etc.) — hand-declared;
  `pID` is its literal primary key, not a child array under something
- 16 single-level child tables, schema-driven (generated by `scripts/schema_codegen.py` from a
  full-population inventory scan — see `docs/tcad_eda/`, not hand-picked): the original 5
  (`property_profile`, `property_characteristics`, `property_situs`,
  `property_legal_description`, `property_identification`) plus 11 more found by a full
  recursive scan of the raw export on 2026-08-17 (`deeds`, `sales`, `permits`, `appeals`,
  `taxingunits`, `inspections`, `events`, `tags`, `links`, `notes`, `smartgroups`) —
  `deeds`/`sales` in particular carry real recorded ownership-transfer history and sale prices,
  more direct fraud-detection evidence than anything else in the database
- `property_owners` / `property_owner_agents` — full owner fidelity (every owner, not just the
  highest-`ownerPct` one; a proper 1:many agent-representation table), superseding the old
  lossy `property_owner` table (archived, dropped from the live database 2026-08-17)
- `property_valuations` — the deep `valuations{}` tree, stored whole as a JSON blob rather
  than normalized

This was originally two separate scripts (a "Stage 1 core" loader and a standalone "Phase 1
EDA ancillary" loader, kept apart while the newly-discovered tables' shape was still being
verified) merged into one on 2026-08-17 once both were schema-driven and fully verified — the
split no longer reflected a real difference, and merging cut two streaming passes over the
29GB file down to one.

**Multi-vintage support**, added later the same day: while re-checking `fetch_tcad.py`, found
a newer 2026 export available on traviscad.org (the 2025 export this project started with was
393 days stale). Rather than just replace one vintage with another, every table's key became
`(pID, pYear)` instead of `pID` alone — `pYear` comes from each record's own field (confirmed
stable across years for the same parcel), so no manual tagging is needed, and multiple
appraisal years now coexist and can be compared directly (spot-checked: the same parcel's
`ownerMarketValue` genuinely differs between the 2025 and 2026 exports — real reappraisal data,
not duplicates). `load_protax_to_sqlite.py`'s `JSON_FILES` list is the single place controlling
which vintages get loaded; adding a new year later is just downloading it and appending its
path there. Currently loaded: 2025 and 2026. Earlier years (2019–2024) exist on traviscad.org
only in the much thinner state EARS format (`docs/tcad_eda/ears_state_reference.md`) — a
different parser, not attempted.

Indexes are created after the bulk insert for performance. Verified to insert every element of
every nested array it handles — full fidelity, including two gaps found and fixed during the
schema-driven conversion: `property_situs` now includes `international`, and `property_profile`
has 75 real columns (up from 22, with the other ~51 no longer buried in an unparsed
`extra_fields` blob).

**Output:** `data/sources/travis_property_tax.db`

After a fresh build, `run_checkpoint` automatically calls `scripts.checks.output_test("stage1")`
to verify the database exists, all 20 tables are present and non-empty, and each schema-driven
table's `extra_fields` column is near-empty (a drift detector — see `scripts/checks.py`).

`scripts/inventory_scan_full.py` and `scripts/schema_codegen.py` remain standalone dev tools,
run by hand only when the schema needs regenerating (e.g. TCAD changes the export structure),
never as part of a normal `main.py` run — see `schema_codegen.py`'s docstring. Full detail on
what's in each table, population rates, and what's still deferred (`ownerTaxable` doesn't have
its own table yet; its raw data sits in `property_owners.extra_fields` in the meantime) lives
in `docs/tcad_eda/`, starting at `00_overview.md`.
