# TCAD Source Data — Table Inventory

Phase 1 of Pivot 2 (see `../fraud_model_pivot.md`): before committing to any
modeling approach, do a comprehensive EDA of the TCAD source data currently
loaded in `data/sources/travis_property_tax.db`. This document is the
starting inventory — what tables exist, their grain, and what each holds.
Later files in this folder will dig into individual tables/fields in more
depth as we go.

**Snapshot date:** 2026-08-17. Row counts reflect the current database build.

**Multi-vintage update (later the same day):** every table described in
this folder is now keyed by `(pID, pYear)` rather than `pID` alone — a
2026 TCAD export was found and added alongside the original 2025 one (see
`docs/project_plan.md`'s "Multi-vintage support" section and
`load_protax_to_sqlite.py`'s docstring for the full rationale). Row counts
and field-level detail throughout this folder were written against the
single-2025-vintage database and are **not** re-verified against the
2026 data — treat specific counts here as historical/2025-only unless
noted otherwise; the schema/fidelity findings themselves (which fields
exist, what's lossy, etc.) still apply to both vintages equally, since
both exports share the same JSON structure.

**Companion documents in this folder**, each covering one part of the
extraction in the same source-structure → fidelity-check → extraction-plan
format, written to eventually anchor code comments back to a documented
structure:
- `protax_extraction_structure.md` — the raw top-level parcel record: what
  `load_protax_to_sqlite.py` extracts (mostly fully, with two caveats) and
  the 12 nested arrays it never touches (`deeds`, `sales`, `permits`,
  `smartgroups`, and others — several look highly relevant to the fraud
  question and were previously unknown to exist).
- `owner_data_structure.md` — the raw `owners[]` array: what
  `load_owners_to_sqlite.py` extracts (lossily) and the full field
  inventory of what a faithful extraction requires (`ownerValue`, `agents`,
  and the deferred `ownerTaxable`).
- `ears_state_reference.md` — notes from the Texas Comptroller's EARS
  manual, used as an external definitional reference for homestead
  exemption sub-types, the value cap mechanism, and ownership-percentage
  semantics.
- `full_inventory_scan.md` (+ machine-readable `full_inventory_scan.json`)
  — the definitive, full-population (486,859/486,859 records) structural
  inventory generated by `scripts/inventory_scan_full.py`, covering every
  distinct field path at every nesting depth across the whole raw export.
  Supersedes the 500-record-sample population percentages quoted
  elsewhere in this folder; several moved substantially once measured
  against the full population (e.g. `deeds` 98%→86.5%, `tags` 95%→81.1%,
  `links` 14%→23.8%).

## Tables

All tables key to `pID` (parcel ID), 1 row per parcel, except where noted.
`properties` is the spine table — every other table's `pID` is a foreign key
back to it. There is also a `sqlite_sequence` table, but that's SQLite's own
autoincrement bookkeeping, not project data.

| Table | Grain | What it holds |
|---|---|---|
| `properties` (486,859 rows) | 1 row/parcel | Top-level parcel record: `propType` (R = residential, etc.), `geometry` (spatial), `inactive`/`inactiveReason` (parcel status), appraisal metadata (`lastAppraisalDt`, `inspectionYr`), roll-correction flags. |
| `property_profile` (486,859 rows) | 1 row/parcel | Exemption and improvement (structure) detail. `exemptions` (TEXT — likely a delimited/JSON list, not yet parsed) is where homestead status lives. Improvement fields: `imprvActualYearBuilt`, `imprvClass`/`imprvCondition`, `imprvMainArea` (sqft), depreciation/pricing factors. `extra_fields` (TEXT) is an unexplored catch-all. |
| `property_characteristics` (486,859 rows) | 1 row/parcel | Land-use and zoning descriptors: `useCd`, `subType`, `zoning`, `region`, `dba`/`sicCd` (business name/classification), irrigation fields (mostly rural/ag, likely sparse in this county). |
| `property_situs` (493,410 rows) | ~1.01 rows/parcel | Physical property address (street/city/zip) — compared against the owner's mailing address for absentee-owner detection. Row count exceeds `properties` by ~6,500, meaning some parcels carry duplicate/secondary situs rows; needs a dedupe rule before joining 1:1. |
| `property_legal_description` (486,859 rows) | 1 row/parcel | Legal/plat description: lot/block, `legalAcreage`, `effectiveSizeAcres`, manufactured-home space number. |
| `property_owner` (486,859 rows) | 1 row/parcel | Flattened primary owner: `name`/`firstName`/`lastName` (entity vs. individual detection), mailing address (`addrCity`/`addrState`/`addrZip`), `ownerPct`, and per-owner value split (`ownerLandHSValue`, `ownerImprovementHSValue` = homestead-treated value; `...NHSValue` = non-homestead). Source for the deterministic dollar estimate (Pivot 2 item 2). |
| `property_identification` (486,859 rows) | 1 row/parcel | Cross-reference IDs only (`geoID`, `refID1/2`, `mapID`, `mapsco`) — no analytical content, just join/lookup keys to external TCAD systems. |

## First EDA targets flagged during this pass

- **`exemptions`** (`property_profile`) — raw TEXT, never parsed open. Homestead
  status lives here; need to understand its format before it can be used
  reliably (current codebase's `has_homestead` logic should be checked
  against whatever this actually contains).
- **`extra_fields`** (`property_profile`) — unexplored catch-all TEXT column,
  contents unknown.
- **`property_situs` row-count mismatch** — ~6,500 more rows than `properties`;
  need to understand why (multiple situs per parcel? historical records?)
  before treating the join as 1:1.
